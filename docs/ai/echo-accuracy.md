# 麦克风回声：过滤效果的实测

本文只有汇总数字，不含会议标题、人名和原文。识别结果只留在内存里，没有写盘。

## 2026-11-02（晚）：识别之前的回声消除

以前是识别出文字后再删回声。现在在识别之前，用会议音频作参考，由 WebRTC AEC3 从麦克风信号里减掉扬声器放出的声音。设计见 `docs/ai/aec-design.md`。

- **存盘**：`microphone.wav` 仍是原始麦克风。
- **重试转录**：在保存的两条 WAV 上跑同一套 AEC。
- **兜底**：文字过滤和音频判断都保留。

### 结论

**外放的回声几乎全部消失，用户的话略有损失。** 11 段双路录音（约 8.5 小时）用重试转录的方式重新识别，AEC 关、开各一次，其他条件相同。AEC 关的数字和上一节完全一致，说明识别本身是可复现的。

| 指标 | AEC 关 | AEC 开 |
| --- | --- | --- |
| 回声词，过滤前 | 33,885 | **15** |
| 回声词，文字过滤后 | 2,065 | 13 |
| 回声行（相似度 0.6），过滤前 | 1,640 | **18** |
| 回声行，文字过滤后 | 170 | 17 |
| 麦克风行 | 4,511 | 2,806 |
| 系统音频里没有的第一人称词 | 927 | 919 |
| 其中被过滤删掉 | 2 | 0 |

外放很响的 4 段（含 11/2 中途切到外放的那段）里，回声行分别剩 0、0、0、5。

**用户的话少了 8 个第一人称词（0.9%）。** 最可能是双方同时说话时 AEC3 的残余抑制压掉的，见下面的双讲测试。原来的过滤只删 2 个，所以按这个指标是净损失 6 个词，换来的是去掉几乎全部回声。

### 声音层面

不经识别，直接比较 AEC 前后的音量。按秒统计，只有数字：

| 录音 | 会议音频播放时，麦克风降低 | 只有用户在说时的变化 |
| --- | --- | --- |
| 外放很响的 4 段 | 中位 32–39 dB | −0.1 到 −0.2 dB |
| 回声很轻的 7 段（耳机） | 中位 0.4–1.5 dB | 约 0 dB |

戴耳机时 AEC 基本不动信号。估计延迟 168–220 ms，在 800 ms 的搜索范围内。149 分钟的那段降幅也保持在 36 dB，没有看到时钟漂移造成的问题。

### 双方同时说话

`scripts/aec-eval.mjs` 在外放很响的录音里取纯回声片段，混入同一个人只自己说话时的真实声音，再和单独识别这段人声的结果比较。**样本很小：** 只找到 4 段，共 55 个人声词、43 个回声词。

| 混入的人声 | 不处理 | AEC 完整输出 | 只用线性滤波 |
| --- | --- | --- | --- |
| 正常音量：保留的人声词 | 38% | 62% | 91% |
| 低 8 dB：保留的人声词 | 5% | 33% | 80% |
| 剩下的回声词 | 58–79% | 0 | 0 |
| 人声能量（正常 / 低 8 dB） | 0 dB | −4.2 / −7.4 dB | −1.4 / −1.4 dB |

- **完整输出比不处理好得多。** 不处理时，识别器会去听回声，人声反而丢得更多。
- **只用线性滤波，双讲时最好，但不能当默认。** 真实外放测试里，它的残余仍然被识别成了大部分词，见下节。

### 真实扬声器

用打包版在临时笔记本里录音，MacBook Pro 扬声器播放一段合成的两人对话，中英文各约一分钟。麦克风里的每个词都是回声。

**实时转录**（经过文字过滤后剩下的）：

| | AEC 关 | AEC 开 |
| --- | --- | --- |
| 英文剩下的词 | 3（删了 15 行） | 0 |
| 中文剩下的字 | 0（删了 3 行） | 1 |

**把同样的录音重新识别、不经过滤**，看识别器听到了多少：

| | AEC 关 | 完整输出 | 只用线性滤波 |
| --- | --- | --- | --- |
| 英文（播放 101 词） | 101 | **0** | 75–93 |
| 中文（播放约 192 字） | 193–194 | **1–3** | 148–163 |

实时 AEC 的估计延迟为 228 ms。每段开头约有 0.3–0.5 秒还等不到参考信号，按超时处理。

### 切换设备后的收敛

用重启时补的静音定位重置点，按秒统计降幅：

- 一段在开头重置的外放录音：第 1 秒起降幅就有 36–61 dB。
- 11/2 那段 21.9 秒切到外放的录音：切换后几秒会议音频很轻，用户可能在说话，第 27 秒起稳定在 34–56 dB。也就是约 5 秒，其中会议音频真正响着的约 2 秒。

### 资源

- **AEC 本身**：约 0.7–0.8% 单核（每秒音频 0.007–0.008 秒 CPU）。
- **实时录音时 helper 的 CPU**：从 4.2–4.6% 升到 8.0–8.1%，多出的部分大多不在 AEC 本身。
- **延迟**：按设计，麦克风文字会晚约 0.25–0.5 秒出现，没有单独测。
- **构建**：helper 多了 4.9 MB 源码，干净构建多约 40 秒。

### 局限

- **双讲样本小**，只有 4 段。轻声插话（比回声低 8 dB）仍会丢掉约三分之二的词，只是比不处理时少丢。下一步可以调 AEC3 的近端检测和抑制参数，或者在双讲时改用线性输出。
- **还没有用新版录过真实会议。** 用户选择先发布，下次外放开会后再看实时数字（诊断里有 `sourceStats.microphone.aec`）。
- **扬声器测试只有回声，没有近端人声**，而且是合成语音。
- **第一人称词只代表一部分用户的话。** 和以前一样，这里的数字都是间接估算。

### 复现

```
node scripts/echo-eval.mjs --audio --levels --aec off|on|linear
node scripts/aec-eval.mjs --jobs 2
native/bin/StillnoteCapture --aec-file microphone.wav --reference system.wav --mic-offset s --reference-offset s [--linear]
```

扬声器测试的脚本放在仓库外：用 `open --env` 启动打包版，通过 CDP 调 `setting`、`create`、`record`、`stop`，用 `afplay` 播放 `say` 生成的对话。

## 2026-11-02：拔掉耳机以后

用户反馈：录音还是有回声，尤其是拔了耳机、换成 MacBook 麦克风以后。实时过滤上线后的第一段真实录音正好就是这种情况，共 36 分钟。

### 设备切换没有出错

- 第 21.8 秒麦克风重启一次，补了 0.72 秒静音。之前麦克风 -72 dB、会议音频 -40 dB，没有回声；之后麦克风紧跟会议音频，相关 0.91–0.96，比它低约 14 dB，是外放。
- 两路时间差在切换前后都是 -80 ms，在过滤器允许的范围内。
- 实时过滤去掉了约 85% 的回声词。只有对方说话的几分钟里，会议音频每分钟约 100 词，麦克风只剩 11–22 词。诊断记录删除 114 行，切片 28 行。

“换了输入以后才有回声”，是因为换成了外放。

### 用户看到的回声是什么

- **碎片：** 切掉回声后，旁边留下的一两个词。原规则是“剩下的一律保留”。这 5 分钟留下 42 行，其中 33 行不足 3 个词。
- **临时文字：** 回声定稿前，会先作为 You 的临时文字出现，定稿后才被拿掉。

### 改了什么

- **用录音本身判断碎片。** 碎片要删，三条都得满足：
  - 会议音频当时在播放；
  - 麦克风没有高过附近已确认回声的音量；
  - 回声响到可能盖住人声时，麦克风还必须紧跟会议音频，响度相关和分贝相关都要达到 0.92。

  符合这个判断的内容，只有两类会删：切片后剩下的部分，以及至少一半词语被会议音频同时说过的短行或走样行。含有系统音频没说过的第一人称词时保留。回声音量的估计不跨过输入重启。实时和重试转录用同一套逻辑，诊断里新增 `echoFragmentsRemoved`。
- **不显示回声的临时文字。** 只影响显示，定稿后照常过滤。
- 采集代码没改。

### 结果

**11 段双路录音，约 8.5 小时**，包括新录音，全部重新识别：

| 指标 | 只看文字 | 加上声音判断 |
| --- | --- | --- |
| 回声词（不过滤为 33,885） | 2,065 | 1,848 |
| 回声行（相似度 0.6，不过滤为 1,640） | 170 | 150 |
| 切片后剩下的部分 | 531 | 376 |
| 其中不足 3 个词 | 224 | **123，少 45%** |
| 声音判断删掉的部分或行 | — | 206 段，共 195 秒 |

**这段 36 分钟的实时录音**：用重新识别找出确认的回声，再判断实时保存下来的行。

- 会删 30 行，其中 24 行不足 3 个词。
- 会议音频播放时的短行从 63 行减到 39 行，少 38%。

**目标没有达到。** 计划是碎片减少至少 70%，实际约 40–45%。剩下的大多是声音显示可能有人声，或者跟随不够紧密，这是为了不误删留的余量。

### 用户的话有没有被误删

| 证据 | 结果 |
| --- | --- |
| 系统音频里没有的第一人称词 | 927 个，少了 2 个，和只看文字时一样 |
| 实时录音被删的 3 个第一人称词 | 都是会议音频 3 秒内说过的同一个词 |
| 把会议音频错开 ±45、±90 秒 | 删除 0 段 |
| 被删的内容又响又不跟随会议音频 | 0 段 |
| 回声很轻的录音 | 被删内容 -64 到 -71 dB，用户说话 -36 到 -42 dB |

**专门检验双方同时说话。** 拿外放很响的 3 段录音里只有回声的片段，把同一个人只自己说话时的真实声音混进去，按 0.6 秒一段判断，统计被误判成“只有回声”的比例：

| 混入的声音 | 误判比例 |
| --- | --- |
| 正常音量（平均比回声低 2–4 dB） | 2.0%（13/660） |
| 比回声低 8–9 dB | 7.0%（40/575） |
| 纯回声被判为回声（作对照） | 75%（576/765） |

回声很轻的 6 段录音里，用户的声音比回声高 15 dB 以上，3,000 多段里只误判了 1 段。

初始阈值在新录音上定，最后的 0.92 是看了这 3 段外放录音的结果选的，所以没有独立的检验集。11 段录音的整体评估在选定之后运行。

### 局限

- **用户比回声更轻声地插话：** 可能被误判，而且越轻越容易，见上表。只有碎片和至少一半已被会议音频说过的行才会走到这一步。
- **自动语言模式的拆句也会产生片段：** 带切片编号的行里有一部分是这样来的，所以“碎片”的数字是近似值。
- **实时效果靠回放估算：** 实时识别的分句比重新识别碎得多。真实效果要看下一次会议。
- 历史会议没有重试。

## 2026-10-31：第一版

测于 2026-10-31，数据是用户自己的 9 场会议、10 段双路录音，共约 8 小时。用保存的音频重新识别一遍，这样才有真实的词级时间。

### 结论

**回声词减少 94%，没有发现用户的话被误删。** 这里比较的是同一批重新识别的转录。

| 指标 | 不过滤 | 旧过滤器 | 新过滤器 |
| --- | --- | --- | --- |
| 回声词（按词估算） | 32,077 | 13,717 | **1,973** |
| 占麦克风词的比例 | 49% | 没有统计 | 6% |
| 回声行（相似度 0.6） | 1,536 行，占 37% | 没有统计 | 159 行，占 5% |
| 整行删除 | 0 | 1,229 行 | 1,297 行 |
| 切掉回声片段的行 | 0 | 0 | 341 行 |

几乎没有回声的两段录音，回声行比例本来就有 2–3%，这是人们自然重复对方用词的结果，所以 5% 已接近底线。按词估算不依赖分句，是更可靠的指标。

### 问题出在哪

1. **这批会议根本没经过过滤器。** 最晚一段录音是 10-28，过滤器 10-29 才提交。所以之前测到的 60–70% 反映的是没有过滤的转录，不是过滤器漏掉的。
2. **最大的问题是混合长行。** 没人停顿时，识别器会把回声和用户的话合成一行，最长的一场平均每行 67 个词。整行删会误删用户的话，所以旧过滤器只能留着。按词算，旧过滤器只去掉 57%，这是主要差距。
3. **中文计分偏严。** 错一个两字词要丢 3 个字对，超过 `gap` 上限；英文错一个词不会。现在对齐仍用字对，覆盖率和间隔按字算，阈值不变。
4. **时间偏移不是原因。** 有回声的录音，两路偏移都在 ±0.25 秒内。
5. **放宽阈值不划算。** 在存档行上回放，只能多拦 125–159 行，其中 7–9 行含有系统音频里没有的第一人称词。所以这次没有放宽，也没有加“确认外放”的门槛。

### 做了什么

- **标准不变，用到行内片段。** 一段词至少 6 个、同一时刻、同样顺序、几乎逐字，才从长行里切掉。
- **只切有词级时间的行，且只在识别器的词边界切。** 切后剩下的内容都保留，哪怕只有一个词。
- **片段里系统音频没说的第一人称词不切。** 片段在这里断开。
- **实时和重试转录用同一套逻辑。** 诊断里新增 `echoesTrimmed`。

### 用户的话有没有被误删

| 证据 | 结果 |
| --- | --- |
| 把系统音频错开 ±45、±90 秒再过滤 | 删除 0 行，切掉 0 行 |
| 系统音频里没有的第一人称词 | 801 个，少了 2 个 |
| 回声很轻的 7 段录音 | 用户说话约 -35 dB，被切内容约 -62 dB，相差约 27 dB |
| 外放很响的 3 段录音 | 被切内容和系统音频的响度相关 0.91–0.95，音量差稳定在 14–15 dB |
| 又响又不跟随系统音频的片段 | 1,781 段里有 25 段，共 111 秒，占切掉时长的 1.1% |

**少掉的 2 个第一人称词都是回声。** 一个在 -66 dB，比这场用户说话低约 30 dB。另一个响度跟随系统音频。两个都是系统音频里的词被听错。

**25 段可疑片段里，没有发现被删掉的整段话。**

- 回声很轻的录音有 17 段，响的部分都不超过 17%，每段不到 1 秒，更像插话的“嗯”或一声咳嗽。
- 所有 25 段的词都和系统音频对齐，偏移不超过 0.25 秒，不符合对方设备把用户声音传回来的特征。
- 外放很响的录音有 8 段，靠音量分不清。其中 2 段按自身延迟对齐后仍和系统音频高度相关，是回声。
- **另外 6 段共 9.6 秒无法排除用户同时在说话。** 即使是这样，切掉的也是系统音频说过的词，用户的话当时并没有被识别成文字。

**排除了“系统音频里混进用户声音”。** 外放最响的两场分别有 185 秒和 252 秒只有麦克风有声，所以用户的声音并没有进入系统音频。

### 还剩下什么

- **零碎片段：** 切后留下 509 段，其中 214 段不足 3 个词。14 段又响又不跟随系统音频，可能是用户的话，其余大多是回声残渣。为了不误删，全部保留。
- **回声词还剩 1,973 个：** 主要是走样太重、不足 6 个词，或者没有连成片段的部分。
- **回声很少的录音降幅小：** 4 段录音回声词本来就不多（62–356 个），降幅是 49–80%。

### 方法

1. 找出同时有麦克风和系统音频的录音，共 10 段。
2. 用 helper 的 `transcribe`（和“重试转录”相同）重新识别保存的音频。真实笔记本只读打开，校验值在每次运行前后没有变化。
3. 回声词：麦克风词在系统音频同一时刻出现的次数，减去错开几秒后靠巧合出现的次数。
4. 回声行：一行至少 60% 的词出现在 15 秒内的某行系统音频里。
5. 音量只保留每 10 毫秒的响度，不保存音频。
6. 复现：`node scripts/echo-eval.mjs --audio --levels`。脚本只输出数字。

### 局限

- **样本小：** 一个人、4 天内的录音。
- **没有实时数据：** 实时过滤还没在真实会议上跑过。实时路径靠单测和 e2e 覆盖；真实录音时，两路到达顺序会不同，只能下次开会后再看。
- **基准不是人工标注：** 这里的数字都是间接估算。第一人称词也只代表一部分“用户自己的话”。
- **6 个词的门槛来自同一批数据：** 没有单独留测试集，但词级时间的结果出来后没有再调整。
- **对方设备传回用户声音时仍可能误判：** 这批数据里没有发现。如果发生，字还留在转录里，只是算到 `Meeting audio`。

### 旧会议

用户同意后，这 10 段录音已在 2026-10-31 用 app 的重试转录处理过。每段都用它原来的语言，只有回声有变化：

- 删除 1,297 行，切片 341 行，和上面的评估一致。麦克风行从 4,132 行变为 3,004 行，系统音频行基本不变（3,569 到 3,571）。
- 待办、笔记和设置都没有变化，其余 9 场会议完全相同。
- 增强笔记随后按用户要求重新生成，共 9 场。旧版本都留在版本历史里，待办没有重新扫描。
- 每段录音都可以在 app 里恢复重试前的转录。只有麦克风一路的录音没有重试，因为它们不可能有这种回声。
